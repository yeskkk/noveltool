# NovelTool v0.17.0

本地运行的小说编辑与分析助手，Python 单进程、浏览器界面、SQLite 单项目文件。程序本身不运行模型，通过兼容 OpenAI Chat Completions 的 HTTP 接口调用用户指定的模型。**这是完整源码，不是补丁；直接安装这一版即可。**

本 README 是程序的整体说明：先说明用户操作，再说明模块、数据流和保存边界。每个版本的差异放在 `CHANGELOG.md`，不是理解程序所必需的前置材料。

## 1. 当前能力与边界

本版本完成至 **M17：恢复、项目维护与整体验收**。原作导入/分块 → 全书分析 → 人工设定与时间线 → 按位置状态 → 上下文装配 → 多个续写候选 → 拼装最终稿 → 确认正文 → 增量同步，这条流程已经接通。没有原作时，可以先由想法生成可编辑的初始设定。

同步复用整个原输入仍然有效的旧分析，补析新增或失效范围。它不等于“模型理解一定正确”；结构、证据通过检查后仍需人工核对。正文先在独立事务中确认；同步失败不会丢失或撤回正文。人工设定永远不被模型覆盖。

公共基础包括本机 WebUI、SQLite 项目、配置校验和定时保存、无损正文块、字符/行范围手工替换、连续撤销、TXT 导入/导出、模型连接测试、结构化输出检查和任务恢复。AI 范围返修也已接通：鼠标/逻辑行选区 → 返修上下文 → n 个候选 → 拼装草稿 → 差异预览 → 原子替换 → 增量同步。返修后可以逐块检查后文，保存带原文证据的可能矛盾；只报告，不自动改文。项目维护页提供中断记录、完整性检查、历史差异和完整备份。M0～M17 的功能范围已经接通，但这是需要真实模型和实际小说继续验收的本地工具，不是“语义永远正确”的自动写书系统。

### 一眼看清主流程

```text

用户想法 ──模型提出初始设定──作者编辑并确认───────────────┤
                                                        ↓
正文位置 + 人物状态 + 相关设定 + 作者本次要求 ──上下文装配
                                                        ↓

                                                        ↓
             显式确认 ──原子追加/范围替换 ──正文 Revision
                                                        ↓
              增量设定同步 ──返修时另做后文一致性检查
                                                        ↓
            作者核对/继续写作；必要时撤销、备份或再次返修
```

阅读顺序：第 2 节启动与首次操作；第 3～4 节理解模块和内存/磁盘边界；第 5～7 节理解正文、切块和模型格式；第 8 节按实际创作顺序解释分析、设定、上下文、生成、确认、同步和检查；第 9～10 节是数据库/API 契约；第 11 节是恢复备份；第 12 节是开发验收。无需先阅读旧版本说明。

## 2. 安装与启动

主要面向 Linux / WSL，Python 3.11 及以上；使用标准库 `fcntl` 取得项目进程锁。运行依赖仅 FastAPI、uvicorn、Pydantic、httpx，不需要 Node.js、npm、向量库或 ORM。第一次安装需要能够取得依赖；安装好后，界面静态资源全部本地提供。网络请求只由明确模型操作发出，目标是你配置的模型地址（该地址也可以在另一台机器上）。

```bash
unzip noveltool-v0.17.0-M17-source.zip
cd noveltool-v0.17.0
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'

# 新项目：正文尚为空。
python -m noveltool --project ../projects/book.sqlite3 --create --title '我的小说'

# 已有项目：不加 --create。
python -m noveltool --project ../projects/book.sqlite3
```

打开 `http://127.0.0.1:8765`。命令行 `--help` 可查看端口等参数。默认只接受本机 Host，不提供登录、多用户和远程共享；不要将端口暴露到公网。

模型配置：在“项目设置”填 `api_base_url`（例如 `http://127.0.0.1:8000/v1`）、`writer_model`、`analysis_model`。模型需要密钥时，在启动前设置：

```bash
export NOVELTOOL_API_KEY='你的密钥'
```

数据库保存的是环境变量**名称**，不保存实际密钥。LLM 请求日志会脱敏 Authorization 中使用的密钥；提示词中的其他私人内容不自动脱敏。关闭“保留 LLM 内容日志”只影响后续及尚未结束的请求，不清除已经保存的历史。

升级：先停止旧程序，再用新源码打开同一项目。打开旧 Schema 时先用 SQLite backup API 生成 `.before-schema-…bak` 文件，再在事务中升级。升级单向；旧程序会拒绝新 Schema。回退必须先停止程序，再打开/复制升级前备份，不能直接把新数据库交给旧程序。源码和项目数据建议放在不同目录。

### 从打开程序到确认一段正文

有原作：先在“导入与分块”核对编码预览、确认正文、建立计划，再到“分析”执行整本书任务；失败项可继续或重试。在“设定”和“时间线”核对模型观察、冲突及人物阶段信息，修改后成为独立人工记录。没有原作则在空项目的“构思”页写想法，检查提案后确认初始设定，再走同一套续写流程。

进入“状态/上下文”检查当前位置资料和预算；在“续写”输入本次要求、A/B/n，必要时先预览模型看到的消息。生成后选取候选片段，编辑最终草稿，确认实际字数，再明确追加到正文。已确认正文可在正文页撤销或手工返修。

确认时默认勾选“同步新增正文的设定”。正文保存后另行启动同步，可在“设定同步”页查看覆盖率、暂停或继续。取消勾选则只保存正文，以后明确点击同步才发请求。下面说明每一步的输入、运算、保存位置和失败边界。


## 4. 启动、内存与保存怎样运作

1. 命令行解析项目路径，创建或打开项目。已有文件不能被 `--create` 覆盖。
2. `ProjectStore` 取得项目旁边的 `.lock` 文件上的 OS 锁，检查 SQLite application ID、Schema 及元数据。锁文件残留不等于进程还占锁，不应手动删除它。
3. `ProjectSession` 载入当前已确认正文与配置，建立异步锁和模型单请求闸门，恢复未完成任务状态。原始导入字节、旧正文块和完整调用日志按需读，不全部复制到内存。
4. 网页配置先经 Pydantic 校验，再更新内存；`data_version` 防止旧页面覆盖新修改，dirty 标记用于默认每 60 秒一次集中保存。
5. 点击“立即保存”或正常退出会保存剩余 dirty 数据。失败时保留 dirty 和错误，不显示“已保存”。
6. 用户确认正文、确认导入、记录分析任务开始/完成等关键边界立即事务保存。为避免丢失已经完成的长分析，每个分块完成是一个额外检查点，不等待下一分钟。

SQLite 使用 WAL、外键检查、busy timeout；本实现选择 `synchronous=FULL`，不是早期草案中的 NORMAL。数据库事务成功后才清除待保存对象。磁盘故障、突然断电和外部损坏并不能因此保证永远可恢复，仍需自行备份。强制终止会丢失尚未提交到服务端或尚未落盘的内容。

正文页的手工编辑缓冲区只存在当前页面，不要在确认前关闭或刷新。续写页的“最终草稿”另有自动同步到内存及集中写盘流程，见第 8 节；这两种编辑器的保存语义不同。正文提交与配置的 `data_version` 是不同的版本计数：`revision_no` 专门用于防止旧正文选区覆盖新正文。

## 5. 正文导入、编辑与撤销的完整流程

### 导入

选择 TXT → 选择编码/分段模式 → 严格解码和规范化预览 → 人工检查 → 确认 → 原始字节、规范化正文、导入 Revision 在同一事务中写入。

自动编码只识别 BOM，否则尝试 UTF-8；不会用“�”替换解码错误。某些旧编码字节也能通过 UTF-8 解码，程序无法保证自动识别正确，因此必须看预览。原始文件最多 20 MiB、规范化文本最多 500 万 Unicode 字符。原始字节保留哈希，下载时校验；正文只统一 BOM 与换行，不擅自丢掉空行和缩进。主小说只能导入空正文。

### 手工修改

正文由保留原有分隔符的 Block 顺序连接而成，不能用“每段之间固定插入两个换行”的方式重建。浏览器以逻辑换行计算行号，视觉自动折行不增加逻辑行。浏览器 UTF-16 选区转换为 Python Unicode code point 偏移；服务端同时核对版本、范围和原文片段。

替换先生成 `RevisionPlan`：被覆盖的旧块退役，新块新建，区间外的块不变。旧块的文本不可修改。事务一起保存 Revision、新块和当前顺序，提交后才替换内存正文。追加同样形成 Revision。字符计数为去除 Unicode 空白后的 code point 数，标点算字。

### 撤销

撤销寻找最近尚未撤销的修改，取回原块并恢复其顺序，再记录一个 undo Revision。不是重新调用 AI“写回去”，因此能够逐字恢复已保存的正文，包括 emoji、空白和换行。只支持向后连续撤销，不支持任意历史 cherry-pick、分支合并或 redo。

## 6. 长篇文本怎样切成可分析的块

`chunker.make_plan()` 读取当前 Block，尽量沿自然边界切分；超长段落使用 `(block_id, start_cp, end_cp)` 切片，不实际改正文。每块有两部分：

- `core`：本次新增分析对象。所有 core 拼起来必须逐字等于全文，不能遗漏或重复。
- `overlap`：紧邻前一块 core 的末尾，仅帮助理解指代和衔接，不重复当作新增内容。

预算从模型上下文 × 安全系数中扣去提示和输出预留；正文采用 UTF-8 字节数加片段开销的保守估计。它**不是目标模型 tokenizer**，不能保证任何服务的精确 token 上限。模型 HTTP 边界还会对完整请求（包含实际 Schema）再检查一次；超预算不会自动丢小说内容，而是明确报错，要求重建更小的计划。

计划保存正文 revision/hash、预算和全部切片。正文或上下文预算变化后计划显示过期。用户可预览实际发给模型的消息；预览不调用模型。

## 7. 模型调用与坏 JSON 怎样处理

所有网络请求由 `LLMClient.complete()` 发往 `{base_url}/chat/completions`，不依赖 tool calling、response_format 或服务端 JSON Schema 支持。密钥从环境读取。默认一次只允许一个模型请求，不自动重试网络错误、不跟随重定向；超时只表示客户端停止等待，不保证服务端立刻停止推理。

只有 `finish_reason=stop` 且正文非空的响应可作为完整结果。截断、HTTP 错误、过大响应和无效协议均明确失败，并保留允许保留的诊断记录。模型响应不得渲染成 HTML，前端用 `textContent` 或 `value` 显示。

结构化分析的边界是：

```text
原始响应 → 引号感知的 JSON 容器扫描 → 重复键/常量检查
         → 必要时仅修单引号与尾逗号
         → 严格 Pydantic Schema（多余字段、隐式类型转换被拒）
         → 证据编号、逐字摘录、实体声明和核心覆盖校验
         → 候选观察，或明确失败
```

不采用“取最长 JSON 就算对”的策略，不补造未闭合对象中的缺失事实。部分纯格式问题可额外调用模型修复，最多两次；缺失必填内容和错误证据不能靠修格式蒙混过关。修复调用只提供坏输出、错误与 Schema，不重发完整小说。每次修复依然经过同样校验。**结构合法、证据摘录存在，不等于结论一定符合原意。**经过修复的结果显式标记 `requires_review`。

## 8. 从一个分块到候选事实

1. 用户选择当前计划的分块。服务在锁内检查正文版本、计划、预算和模型名，形成不可变输入快照。
2. Python 给切片分配 `B001` 等短引用；模型只看到短引用，不看到项目 UUID。引用映射会留作审计。
3. 立即保存 `analysis_runs.status=running`，释放项目锁，发送分析请求。facts 模式提取实体、相对稳定的事实、阶段状态和事件。
4. 完整结果经过结构与证据校验。每条观察至少引用一份 core 证据；只引用 overlap 的记录被拒绝。
5. Python 将短引用转回不可变正文块及切片范围，保留逐字摘录，创建 `observations`。证据范围是来源切片，不假装是模型推断出的精确事件发生时间。
6. 在一个事务中保存观察和运行结束状态。默认 observation 是 pending，不改变正文。
7. 等待期间正文发生修改时，结果标记 stale，隔离保留以供检查；不会混入新版本的有效结果。失败可重试，重试新建 run，旧记录不会覆盖。
8. 正常取消留下 interrupted；启动发现 running 遗留也改为 interrupted，由用户选择重新执行，不偷偷重发请求。

### 全书分析：程序内任务和恢复

点击“开始 / 继续”会先保存一个 analysis_jobs 记录，然后由程序内持有引用的 asyncio Task 顺序遍历分块与任务类型。不是外部队列，不并发挤压小模型。facts、links、narrative 被拆成三个窄任务；每种输出使用独立必填 Schema，不要求一次抽出所有内容。

每次执行前检查当前正文、计划和模型配置。已经成功的 `(计划, 分块, 类型, Schema)` 直接复用；勾选重试时只重新尝试未完成/失败的部分。某个分块的结构化输出失败不妨碍下一块；连接中断、服务错误和超时会暂停，避免连续轰击不可用服务。返回 done 只代表选中任务都有结构化结果，不代表语义绝对正确。

暂停是协作式：等当前请求结束并保存后不再发送下一请求。程序退出会取消并等待内部 Task，再关闭数据库；服务端是否继续计算不受本程序控制。再次启动不自动联网，遗留任务变为 interrupted，由用户点击继续。继续新建 job 审计记录，同时复用已有成功结果。

### 自动归并：原始观察不是数据库操作指令

KnowledgeService 使用 SemanticSync 在当前正文中验证过完整原输入的成功 run，跨计划和正文版本复用；同种任务出现重叠范围时以最近成功的输入范围为准，失败重试不抹掉旧成功结果。观察从磁盘读取后重新验证 Schema 和证据，再建立内存视图；未变更时直接使用缓存，不每次查询全库。原始观察、旧计划和运行日志仍保留作为历史。

实体名只做 Unicode NFKC、首尾/连续空白归一和 casefold，同类型同名自动聚合；不做模糊匹配，不擅自认定“林先生”和“林”是同一个人。不同实体种类出现同名时，无法唯一解析的引用进入待审区。相同稳定事实归并证据，不同取值并列为冲突；阶段状态按证据在正文中的位置排列，不覆盖历史。关系保留方向，A 信任 B 不等于 B 信任 A。事件只做相同内容、相同证据位置的严格去重，不能把不同章节的重复事件合成一次。

修复过且未人工接受的记录、模型标为 uncertain 的事实不会混成确定设定。叙事摘要是分块局部摘要，没有假装一次读懂全书，也尚未生成一个不断覆盖的全书摘要。

自动归并不依赖“最后打开的计划”。旧输入的 core 与 overlap 块均未退役、切片仍连续且前后紧邻、核心哈希一致时，原观察仍可用。修改了输入中的任何块便隔离整个 run，不能只因其中一句摘录尚在就复用结论。证据字符位置表示“叙述到这里才提取到此信息”，不是故事实际时间；倒叙不能靠简单排序自动解开。

### 设定、人工修改和模型观察如何并存

`SettingsService` 在启动时载入人工实体和记录，`KnowledgeService` 以“正文版本 + 分块计划 + 自动观察 + 人工版本”缓存当前视图。人工表和观察表分开，模型分析只能产生 observation，不能更新人工表。打开设定页面不调用模型。

人物卡片允许编辑姓名、别名、种类、备注；同类型的人工姓名/别名冲突会报错。为自动人物建立人工事实时，服务同时固定该人物身份，避免重建分块计划以后人工事实变成悬空引用。别名匹配是确定性的；程序不会偷偷用模糊匹配把两个人合并。

新建记录时先选择事实、阶段状态、关系、事件、线索或笔记。选择涉及人物、字段及值；阶段记录可输入逻辑行并定位到正文，或直接指定字符位置。全局事实不必定位。没有正文时不允许建立“已经发生”的事件，构思计划应记为 planning 笔记。事件支持手工录入故事时间文字和排序值；未知时间保持空，不能把叙述顺序冒充实际故事时间。

自动条目可点“转为人工记录”：复制内容及来源到普通表单，你修改后确认。相同人物、字段和位置的人工事实成为有效取值，原自动冲突仍可展开查看。直接新建的人工条目也有锁定意义。这里的锁定表示模型不能改这条记录，不等于永远冻结人物未来状态。暂时停用人工记录会恢复相应自动视图，不删除历史。

确认过程是：服务核对页面的语义版本 → 校验实体引用、Schema 和位置 → 生成变更及审计 → 一个 SQLite 事务提交 → 更新人工内存对象和视图缓存。旧页面、重复的有效字段、无效引用及磁盘失败不会部分覆盖现有数据。审计记录保留修改前后，当前没有任意历史恢复按钮。

### 位置锚点、返修影响与审核边界

人工位置保存为不可变 `(block_id, offset)`，界面行号只是当时的输入方式。前文插入使后文移动时，根据当前块顺序重新计算位置；一旦该块本身被返修替换，记录显示“位置失效”，保留内容但不参与有效设定，必须重新定位或停用。全局人工事实不受正文换块影响。自动观察通过完整输入依赖校验决定是否有效，不通过全文 revision 直接淘汰；撤销恢复原块时，符合条件的旧分析可重新进入当前视图。

“接受观察”只表示人检查过本次分析记录，允许修复结果参与自动视图；**不等于将其锁为人工设定**。后续重分析会产生新观察。要长期保留修改，请转为人工记录。拒绝的观察不参与当前视图，可在筛选器中恢复；被旧分析替代的历史观察不能通过审核按钮重新混入新结果。

时间线页可按正文叙述位置或人工填写的故事排序查看事件，同时编辑关系与线索。时间线展示变化记录；完整的按位置状态计算和上下文检查由“状态/上下文”页面提供。


### 没有原作时：想法 → 提案 → 草稿 → 人工设定

空正文项目打开“构思”，输入想法与明确限制，选择本次输出 token 预留。服务核对正文为空、模型可用、设定版本未变以及完整提示预算，立即保存 idea_proposals 的 running 记录，再释放项目锁请求分析模型。这个入口不会修改正文，也不分析不存在的历史事件。

IdeaResult 的顶层字段全部必填：前提摘要、实体及初始事实、关系、潜在线索、风格建议。模型只使用本次实体名/别名，不能生成数据库 ID。除了统一 JSON 校验，还检查名字和别名是否唯一、字段是否重复、关系是否引用两个不同的已声明实体，以及线索是否引用有效实体。输出经过修复时仍提示人工核对，不自动接受。

成功后保存原始结构化提案和一份可编辑草稿。网页用普通表单展示人物、字段、取值、关系等，不要求用户手写 JSON。可以删掉不需要的条目、补充或修改内容。点击“只保存提案草稿”立即写盘，但不会改变设定；草稿版本防止两个页面相互覆盖。关闭前尚未保存到服务端的表单内容仍可能丢失。

点击确认时重新校验整个草稿和生成时的正文/设定版本。Python 解析名称为内部 UUID，建立完整的人工记录计划，然后在**一个事务**中写入人物、事实、关系、待定线索、前提/风格笔记、操作审计，并把提案标为 accepted。任一步失败全部回滚；只在 COMMIT 成功后发布人工内存数据。正文 revision 保持不变。这里的线索 status=uncertain，表示潜在规划，不创建 timeline_event 或已发生状态。

匹配已有人工人物时保留原人工姓名、别名和备注；同字段同值复用，不同值冲突时拒绝整次确认。不会替你覆盖已有人工设定。生成之后改过正文或设定，提案仍能查看和另存草稿，但不能直接确认；需要核对当前项目并重新生成。当前不实现自动 rebase。

历史提案包含失败或中断状态。再次启动会将遗留 running 标为 interrupted，不偷偷重新调用 API；用户决定是否重试。已有正文的项目不能使用初始化入口覆盖世界，应在设定页进行人工编辑。


### 状态计算：先限制可知范围，再做归并

StateReducer 首先取当前位置以前的有效观察，并取此处已经生效、没有失效锚点的人工记录，再调用相同的归并逻辑。不能先把全书归并成最终状态再删掉后文，因为这样未来冲突、后期关系和人工覆盖可能已经污染早期结果。未出现的自动实体也不提前带入；全局人工档案和无位置的初始设定则是作者明确给定的全局资料。

同一字段依次应用 set、add、remove。一个确定 set 会设置值；两个不同的自动 set 落在同一叙述位置时不凭 UUID 决定胜负，而是显示 conflict/未确定。同位置的明确人工 set 优先，但不冻结未来：后面的状态仍然可以继续变化。带位置的人工事实从自己的锚点起作为明确设定生效，不会被更早的状态倒过来覆盖。

add/remove 管理已知集合；没有完整初始集合时，显示 partial/部分已知，不能因为只记录了“拿到钥匙”就声称人物只有一把钥匙。同时增加和移除同一项且没有先后依据，显示冲突。字段名仅做明确的 Unicode/空白归一，不把“地点”“位置”擅自认定为同一个字段；需要作者人工统一。

关系保留 A→B 方向，线索取此处之前最后适用的状态。未来才解决的问题在早期仍然开放。修复后未审核的观察、不确定事实、失效锚点不会成为确定状态。自动记录的可知位置是证据来源切片末尾，宁可少带早期信息，也不把可能依赖后文的推断提前泄露。

这是**叙述位置视图**，不是故事真实日历模拟。倒叙、梦境、不可靠叙述和人物谎言仍可能被小模型误判。程序不能凭文本位置自动解决这些语义问题；界面会提醒人工检查，用户可修正记录与位置。

### 写作上下文：资料选择和预算怎样工作

ContextBuilder 检查正文 revision 和语义版本，续写取末尾状态，返修取选区开始前的状态。系统规则、本次作者要求、A/B、完整返修目标及紧邻正文窗口是必需部分。紧邻后文单独标为“用于承接”，不能混成当前位置已经发生的事实。作者显式固定的实体也成为必需项，不能为了凑预算偷偷删除。

其余资料先做轻量检索：作者要求、邻近正文和选区中匹配姓名/别名，扩展一层直接关系；没有命中时只取一个小的候选集合。使用普通字符串和拉丁词边界，没有 embedding。逐个实体加入此刻已知字段，冲突不选定取值，部分集合明确标注。作者前提/风格、较近正文、相关关系、开放线索、局部摘要和旧事件按优先级尝试加入。

每加入一个可选项都对**最终消息的实际序列化内容**重新估算预算；包含 JSON 包装与消息开销，不只是加正文字符数。输入与输出预留之和必须小于安全预算。默认输出预留为 `max(512, 4 * B + 256)`，也可手动设置。它是保守规划，不是目标 tokenizer；精确长度与推理 token 行为由实际服务决定。

必需项放不下时明确报错，要求缩小返修范围、缩短指令、取消固定实体或调整输出预留，绝不截掉返修目标一半。可选项放不下就记录为 dropped，用户可展开查看省略内容。最终 ContextPackage 带有完整 messages、每项标签和来源 ID、估计开销、包含/省略列表、基线版本及指纹。内部 UUID 只留在调试元数据，不作为小说资料传给模型。

“状态/上下文”页支持按逻辑行定位、直接字符范围或鼠标选区；UTF-16 选区转换为 code point。点击预览只计算数据包，不调用模型、不写入正文，也不自动批准设定。候选生成复用这个入口，并保存确切的上下文快照，不另写一套偷偷拼接的 prompt。


### 续写候选：n 次独立请求，不是一个请求输出 n 段

在“续写”页填写本次指令、A/B/n，可先预览上下文。创建任务时，ContextBuilder 核对版本并装配最终消息；GenerationService 再记录本次模型配置、温度、字数、候选数和完整 ContextPackage。开始记录立即写入 SQLite，再启动由服务持有引用的程序内 Task。不是外部队列，也不是程序退出后还能运行的守护任务。

任务顺序执行 n 次 Chat Completions 请求，每次只要求一份纯小说正文，没有 JSON 外壳，不依赖服务实现 n 参数。请求之间不放入彼此的候选，使用相同的上下文快照及温度。采样不保证候选一定不同；完全相同的文本会显示重复提示。一次只能有一个模型工作流，全书分析、构思和测试不能抢占正在执行的候选任务。

每个请求开始创建 generation_attempts 记录。正常返回后只去除首尾空白，检查 Unicode 和字符数；符合 A/B 标为 complete，范围外标为 length_mismatch。两种文本都保存供人检查，但范围外不冒充合格结果，不自动截断句子凑字。若用户需要严格范围，必须重新生成或手工改到范围内；本阶段不承诺小模型每次都会遵守字数。

截断、拒绝、空输出等保留失败记录，不当作完整候选；连接、HTTP、协议或超时错误暂停后续请求，避免自动轰击不可用服务。单项失败不删除同槽位上一次成功文本；界面能展开全部尝试。继续任务只补没有可用文本的槽位，超范围但已返回完整文本的槽位需明确点击单项重试。

每个完成候选是事务检查点，已经返回并保存的结果不等整批结束。当前任务及尝试在内存缓存中，频繁轮询不重复扫描 SQLite；历史任务按需加载，缓存最多保留 16 份快照。暂停等待当前请求结束并保存；退出会取消并等待 worker 后再关闭数据库，重开显示 interrupted，不自动联网。

创建后修改项目 A/B/n 或模型只影响新任务，当前任务和重试继续使用原快照。修改正文或人工设定则停止旧任务后续请求；已经返回的旧候选可查看，但不能直接套到新基线。模型过程中不持项目锁，因此用户仍可编辑项目；服务器端是否继续计算取消请求不受本程序控制。

返回的候选仍不是正文。下面的草稿与确认阶段由用户明确操作，不自动选择某个候选，也不因为候选内容更新人物状态。


### 候选拼装：浏览器缓冲、程序内存和 SQLite 的区别

每个候选提供“全部采用到草稿”和“选中文字插入草稿”。选段按浏览器当前选区取出，在最终草稿的光标处插入；不调用模型，不暗中增加过渡句。作者可以自由删除、补写，甚至完全不用候选。覆盖非空草稿会先确认。正文计数仍以非空白 Unicode 字符为准，浏览器明确匹配 Python 的空白集合，包含标点。

最终草稿有三个层次：浏览器 textarea → 程序内存 PendingDraft → SQLite generation_tasks。停止输入约 900 毫秒后，前端把当前文本和 `expected_draft_version` 发送到程序内存；只有合法字符和匹配版本才更新。PendingDraft 记住最新文本、内存版本和原始磁盘版本，并设置 `generation_drafts` dirty。此时正文和设定都没有变化。

默认每 60 秒，ProjectSession 在一个事务中把所有待保存草稿、配置和调用日志集中写入。点击“立即保存草稿到磁盘”、其他成功检查点或正常退出也会保存。写盘成功才清除 PendingDraft；失败则保留内存文本、dirty 和错误。草稿热缓存与历史任务缓存配合，不为每次轮询重新查询数据库。强制杀死程序仍会丢失尚未落盘的草稿，浏览器尚未同步的输入也可能因关闭页面丢失。

前端串行化草稿请求。模型候选轮询不覆盖编辑区，老的网络响应不覆盖较新的草稿版本；请求期间继续输入会在下一次请求同步。发现另一页修改时保留本页文本，显示冲突，要求先复制保留再显式重新载入或重试；不会静默选择某一页。任务生成仍在进行时可以起草，必须等任务结束或暂停后才能确认正文。保存草稿本身不使该任务的正文/设定基线过期。

### 正文确认：一个事务，不是一串半成功操作

点击“确认追加到正文”后再次询问用户；界面先保存草稿，后端仍会独立校验最终文本。最终稿必须非空，符合任务 A/B；作者明确勾选允许超范围时才放行范围外的最终稿。候选的长度不约束人的编辑权，但不会默默取消检查。

服务在项目锁内依次核对：任务不是正在运行的候选任务 → 当前正文与设定仍匹配任务快照 → 草稿版本一致 → 文本与范围合法。然后 RevisionEngine 生成 append 计划，保留作者最终稿的缩进、空白和换行，并按新段落规则追加；不会原地改掉旧 Block。

持久化阶段在**同一个 SQLite 事务**中写入待保存草稿、Revision、新正文块和任务 committed 状态，同时记录 `committed_revision_id` 与最终稿哈希。只有 COMMIT 成功才发布内存正文并清除草稿 dirty。任一步失败都会回滚正文和任务状态；已有候选、已确认正文和内存草稿保留，允许修复磁盘后重试。日志/其他 dirty 数据也遵守同一事务边界。

同一任务确认后不可再次生成或修改这份历史草稿；修改已确认内容使用正文页。相同最终稿重复确认只返回原来的 revision，不再追加，即使用户此前已撤销那次追加也不会偷偷恢复。不同文本重复确认会拒绝。正文页现有连续撤销功能仍能逐字恢复确认前的正文；候选和历史确认不会从审计中消失。

### 增量同步：正文确认之后发生什么

1. 正文和 Revision 先原子保存。HTTP 确认入口在事务成功后，才根据 `sync_after_commit` 决定是否启动独立同步；模型未配置、忙碌或启动失败时，确认仍返回成功并明确提示待同步，不假装同步成功。
2. SemanticSync 读取成功分析的原始引用。core、overlap 的全部块必须仍在当前正文中，范围合法、内部连续，overlap 仍紧邻 core，核心哈希一致。模型输出中的一句证据幸存，不足以证明整次分析可复用。
3. 按任务类型选择互不重叠的最新有效输入范围，计算 facts/links/narrative 的 Unicode 字符覆盖率。失败的重试没有替代权；新成功的空结果则可以明确替代旧结论。覆盖率是处理进度，不是准确率。
4. 创建新计划时尽量保留兼容旧模型配置下的块边界，在缺口处用有限预算的普通切块补齐，并重新计算前置重叠。完整 core/overlap 与原输入完全相同时，用 `analysis_reuse` 指回旧 run，而不是复制 observation 或伪造新的模型调用。
5. 所有观察的原 ID 和人工接受/拒绝状态保留。旧来源仍有效时，可以继续审核；已失效、被更新分析替代的观察不能通过审核混回当前设定。模型、服务地址或上下文配置改变时，明确同步将重新请求不兼容单元。
6. 复用 AnalysisJobs 顺序运行缺少的 `(块, facts/links/narrative)` 单元，每完成一次便保存检查点。结构失败保留失败记录，其他块可以继续；连接失败暂停。同步页面显示各类覆盖、待审数量、作业进度、错误和暂停按钮。
7. 如果正文在模型运行中再次改变，正在返回的旧版本结果隔离，后续请求停止。重启不会自动联网；点击同步会为当前版本重建缺口计划并复用完成部分。

当前正文、有效旧观察和人工设定是热数据/缓存；历史原输入和旧记录从 SQLite 按需读取。更改正文触发缓存重算。全局人工事实保留，人工位置锚点随块退役失效并等待人工重新定位。

**同步完成与因果一致是两回事。** 返修第十章的钥匙交接，即使第十五章文本完全未变，该后文仍可能矛盾。复用表示抽取来源有效，不代表剧情已自动修好。ConsistencyService 另做下述提示性检查；不自动级联修改后文，也没有无限自动重试。

AI 返修与手工范围替换均已可用。AI 返修确认时可自动同步；手工改文后可明确点击“设定同步”复用未受影响的资料。

### AI 返修：如何把行范围安全地变成一次替换

在正文页用鼠标选中已有文字，再点击“AI 返修当前选区”；也可以先按逻辑行选中，再进入 AI 返修。在“续写/返修”页直接切换为返修也可以，页面提供原文只读框、鼠标选区、起止逻辑行和字符位置。跨页链接只带正文版本和位置，不把小说全文放进 URL；旧版本链接不会被静默套到新正文。

生成之前，ContextBuilder 取选区开始前的人物状态、完整选区、邻近前文和单独标注的后文。目标文本是必需上下文，超预算必须缩小范围，不允许截去目标一半。A/B 指每个候选替换文本的长度，不是替换后整个章节的字数。

GenerationService 在创建任务的同一个事务中保存 RewriteTarget：原正文 revision、起止 code point、完整选区原文、SHA256、所有来源 Block 切片。选区以 `[start,end)` 定义，浏览器先把 UTF-16 位置换为 code point；中文、emoji 和跨段落都不按字节切。真实 Block ID 只由 Python 生成，模型不能指定。

之后与续写共用候选、独立请求、重试、草稿拼装和保存机制。界面始终展示该任务冻结的原选区，防止把返修稿误当续写稿。差异预览比较原选区和当前最终稿，不写正文，也不调用模型；最多显示 600 行差异，超过时明确提示，完整原文和草稿仍可查看。

点击“确认替换原选区”才提交。后端再次验证任务/设定/草稿版本，重建当前选区的 Block 切片并与快照逐项比较。任何不匹配拒绝确认。RevisionEngine.replace 保留 `原文[:start] + 最终稿 + 原文[end:]`，覆盖到的首尾块整体退役，新块重新分段，范围外文字逐字不动；**不会自动插入段落分隔符**。作者需要空行时必须放在草稿中。最终稿与原选区相同则不创建无意义 revision；空白删除请用手工替换。

返修 Revision、任务确认状态、最终稿和待保存日志在一个事务中保存；磁盘失败全部回滚。重复确认返回原历史 revision，不再次替换；撤销恢复原块和原文。有效来源判断会隔离涉及退役块的旧分析；增量同步复用其他有效单元。后文可能仍有因果矛盾，此版本不自动修改它们。

### 返修后的一致性检查：完整后文覆盖，不自动修复

AI 返修确认面板默认勾选“检查后文一致性”；`check_after_commit=false` 只关闭这次自动检查，不影响正文确认。同时勾选设定同步时，先确认正文，再排队等待该同步任务结束，然后检查后文，避免同时挤压小模型。即使同步失败，检查仍可直接使用正文证据；若已有其他模型工作流占用，则暂停并要求明确继续。

手工范围替换之后，可以进入“一致性”页面明确点击开始。当前入口只比较**最新一次 rewrite/manual_edit Revision**；追加、撤销、被后续正文修改超过的旧 revision 不在可新建检查的范围内。旧检查仍可查看，但不允许在新正文版本上继续旧任务。全篇返修没有后文时显示“不适用”，不会浪费模型请求。

流程分为六步：

1. 利用不可变旧 Block、当前正文和 Revision 的哈希/选区重建修改前后原文。必须逐字验证范围外内容未变；无法验证就不发送请求。
2. 把完整旧选区和完整新选区固定为必需资料，将选区之后的所有正文切为有序、无遗漏、无重复的检查单元。每次调用都带完整修改对比及一个后文单元。过大的改写对比放不下时明确报错，必须缩小返修范围或调整预算，不偷偷省略修改内容。
3. 保存任务配置、实际 messages、B 编号对应的文本和不可变 Block 切片。启动和继续时重新核对整份输入清单、覆盖连续性和预算；外部损坏或篡改的输入不发送给模型。
4. 模型只返回 `issues`。每条问题必须有严重度、标题、带不确定性的解释，以及至少一条旧/新选区证据和一条本单元后文证据。证据编号、角色和逐字摘录都检查；没有真实原文支持的问题被拒。原始模型仍可能误读梦境、谎言和倒叙，因此通过检查不等于判断正确。
5. 每个完成单元在事务中保存结果、证据和调用引用。结构错误只使该单元失败；网络错误暂停，继续时只补未完成单元。已完成范围和失败范围分别统计。程序退出取消并记录 interrupted；重启不自动发请求。
6. 页面显示检查了多少后文字、哪些单元失败、问题来自哪段原文。作者可把问题标为待处理/已处理/忽略；版本号阻止旧页面覆盖新标记。这个按钮只改变检查状态，不会修改正文、人工设定或自动观察。修复过的模型输出会显式标注待人工核对。

**没有问题列表，不代表小说已经证明一致。** 此检查只比较本次修改与提供的各块后文，不是跨任意远隔段落的全局推理引擎。分块边界和有限模型能力会漏报；新问题也可能有合理解释。检查期间作者修改正文，返回结果只作为旧版本历史保存，当前覆盖不再计入。无论模型、格式校验或保存检查结果是否失败，已确认正文都不会回滚。

## 9. 数据库和版本的对应关系

项目 Schema 当前为 **14**，SQL 脚本按三位编号顺序执行；应用版本和 Schema 版本不是同一个数字。只有已实现的表进入数据库。

| 数据 | 保存位置及职责 |
|---|---|
| 项目/配置 | project_meta、project_config；当前配置和保存版本 |
| 正文历史 | manuscript_blocks、revisions；不可变文本块及顺序变化 |
| 导入/切分 | source_imports、chunk_plans；原始文件与可验证的计划 |
| 模型调用 | llm_runs；内容日志可关闭，元数据仍保留 |
| 分析 | analysis_runs、observations；任务状态、证据和候选记录 |
| 增量复用 | analysis_reuse；新计划单元映射到原成功 run，保留原观察身份 |
| 全书任务 | analysis_jobs；任务配置快照、暂停/中断状态，进度从已保存分析记录计算 |
| 人工设定 | setting_entities、setting_entries；独立人物档案、事实/状态/关系/事件/线索/笔记 |
| 人工审计 | setting_changes；每次确认修改的前后数据和独立版本号 |
| 构思提案 | idea_proposals；原始想法、模型结果、可编辑草稿、版本及确认状态 |
| 续写任务 | generation_tasks；原始参数、上下文/配置快照、草稿版本、确认的 revision 引用及任务状态 |
| 返修快照 | generation_rewrite_targets；原始选区、来源切片、版本及哈希，不随草稿变化 |
| 候选尝试 | generation_attempts；每一候选的每一次尝试，不覆盖旧的成功文本 |
| 一致性检查 | consistency_jobs、consistency_units、consistency_issues；修改来源、完整后文输入单元、检查点和人工处理状态 |

不要直接用外部 SQLite 工具在程序运行时修改项目。程序持有内存投影，外部写入可能破坏一致性；本机 advisory lock 只约束遵守它的程序。需要手工操作时先停止服务并备份。

## 10. HTTP 与界面的边界

`GET /health`、`GET /api/status` 查看运行/保存状态。`GET /api/config` 和 `PUT /api/config` 处理配置；`GET /api/manuscript` 读取正文，正文写操作有 expected revision。

导入入口位于 `/api/import/*`；模型诊断位于 `/api/llm/*`；分析入口为 `/api/analysis/chunks/{ordinal}/preview`、`.../run` 和 `/api/analysis/runs`。ordinal 从 0 开始，页面从 1 显示。

所有写操作先从 `GET /api/session` 获取 `csrf_token`，通过 `X-Noveltool-Token` 请求头发送；接受 JSON 的写接口必须使用 `Content-Type: application/json`，原始 TXT 上传接口例外。保护包含本机 Host、同源检查、CSRF 令牌和请求体上限，不是账户系统或强认证。不要把其他不可信网页/软件视为受这些机制彻底隔离。

全书任务使用 `POST /api/analysis/jobs`、`GET /api/analysis/jobs/latest`、`POST /api/analysis/jobs/{id}/pause`。`GET /api/knowledge` 只返回自动归并视图，不调用模型。单块请求的 `pass_type` 为 facts/links/narrative；全书请求的 `passes` 指定要运行的任务种类。

`GET /api/settings` 获取完整当前视图及语义版本；`POST/PUT /api/settings/entities[/{id}]` 编辑人物等实体；`POST/PUT /api/settings/entries[/{id}]` 编辑记录；`POST .../entries/{id}/disable` 停用记录；`POST /api/settings/review` 接受/拒绝/恢复自动观察。所有修改传 `expected_version`，不是只比较正文 revision。`GET /api/settings/position?line=1&edge=end` 将逻辑行换算成字符位置，`GET /api/settings/history` 返回最近 100 次人工操作。

构思页面为 `/ideas`；`POST /api/ideas` 生成提案，`GET /api/ideas` 列出最近 100 条历史，`GET /api/ideas/{id}` 查看详情；`PUT .../{id}/draft` 只保存提案，`POST .../{id}/accept` 在事务中确认初始设定。草稿写操作有 `expected_proposal_version`；生成和确认还核对 `expected_version`（语义版本）。

`GET /api/state?at_cp=N` 计算指定字符位置（缺省为正文末尾）的视图；`POST /api/context/preview` 接受 continue/rewrite、正文与设定版本、指令、A/B、可选输出预留和固定实体。返修必须提供非空 `[start_cp,end_cp)`；续写固定在末尾。返回完整 messages、输入估计、输出预留、安全预算、必需/可选资料与省略原因，不调用模型。

`POST /api/generation` 接受 `{context: ContextRequest, candidate_count: n}` 并返回 202；`GET /api/generation` 列历史，`GET .../{id}` 查看候选；`GET .../{id}/context` 获取当时的完整消息。`POST .../{id}/pause` 协作暂停，`POST .../{id}/resume` 继续没有可用结果的槽位，`POST .../{id}/regenerate/{index}` 单独重试指定槽位，index 从 0 开始。continue 与 rewrite 共用这个 API；rewrite 要求合法的非空选区，并保存独立选区快照。

`PUT /api/generation/{id}/draft` 接受 `{text, expected_draft_version, force_save}`；默认只更新程序内存，`force_save=true` 立即批量写盘。返回的 `draft_version`、`saved_draft_version`、`draft_dirty` 和 `draft_save_error` 区分内存与磁盘。

`POST /api/generation/{id}/commit` 接受 `{text, expected_draft_version, allow_out_of_range, sync_after_commit, check_after_commit}`。后两项缺省为 true；check_after_commit 只用于返修，一致性任务在已启动的同步结束后执行。sync_after_commit 为 true 时，HTTP 入口在正文保存后尝试启动同步；false 只保存正文。检查任务基线和草稿版本，再根据任务类型原子追加或替换正文；返回 `task`、`revision`、`current_revision_no`、`already_committed` 与 `semantic_sync`（running 或 pending）。相同已确认任务、相同文本的重复请求返回同一次历史确认，不重复追加；不同文本则冲突。即使此后撤销了正文，也不允许借重试恢复已撤销文本。没有自动 rebase。


`GET /api/sync` 返回当前覆盖和最近分析作业；`POST /api/sync` 接受 `{expected_revision_no, settings?}`，生成增量计划并返回 202、复用数及 job。`settings` 可选，格式同 PlanSettings；省略则使用最近分块参数。暂停沿用分析作业 pause 接口。

`POST /api/generation/{id}/preview` 接收 `{text, expected_draft_version}`，只返回返修前后原文和统一差异。提交仍使用相同 commit 接口，由任务类型决定追加/返修，不由客户端再次指定任意目标范围。

`GET /api/consistency` 列出最近 100 个检查，`POST /api/consistency` 接受 `{expected_revision_no, output_reserve}` 检查最新返修。`GET .../{id}` 返回进度、覆盖和问题；`POST .../{id}/pause` 或 `/resume` 暂停/续跑。`GET .../{id}/input/{ordinal}` 展示保存的真实输入和来源。`PUT /api/consistency/issues/{issue_id}` 接收 `{expected_version, status}`，只改变人工处理标记。

## 11. 项目维护、备份与退出恢复

打开“项目维护”可以查看当前正文 revision、Schema、内存待保存部分、上次保存错误、SQLite/WAL 文件大小、本次启动接管的未结束任务，以及最近的中断/失败记录。只读列表不会续跑任务；必须到对应工作页面核对基线，再明确继续。启动恢复计数在各服务把遗留 running 改为 interrupted **之前**记录，因此不是把历史失败误说成这次刚发生的崩溃。

### 完整性检查

“检查当前项目”会核对期望正文版本，再在项目锁内执行 SQLite integrity_check、foreign_key_check、全部当前及历史正文块哈希、原始导入文件哈希、revision 序号和前后哈希链、磁盘当前正文与内存正文一致性。检查只读，不自动修复。错误过多时只列前 200 条，并给出完整计数；大项目检查会暂时阻塞编辑和保存，所以只在用户点击时运行，不每分钟扫描一次。

这不是所有 JSON 字段和全部历史变更逻辑的形式化验证，更不检查小说语义。不同服务在真正使用数据时仍会再检查自己的 Schema、来源和版本。检查通过不保证硬盘未来不会故障；发现损坏时保留原文件，先用独立备份恢复，不要继续让程序覆盖问题文件。

### 完整备份与恢复

点击“保存并下载完整项目备份”后，服务先核对正文版本，集中保存已经同步到程序内存的草稿、配置和日志，再用 SQLite backup API 创建独立数据库文件。不是只复制主 `.sqlite3` 文件而漏掉 WAL。备份包含原作、当前正文、设定、观察、候选、修订历史和已保留的模型日志，不包含浏览器尚未发送的内容，也不包括外部环境变量中的 API key。小说本身和提示中仍可能含私人资料，请妥善保管。

下载前使用独占、仅文件所有者可读写的临时文件并做 quick_check；响应发送完后删除临时文件。程序在下载过程中被强制终止时，系统临时目录里可能留下私有备份临时文件。浏览器接收后用 Blob 保存，因此非常大的项目会占用额外浏览器内存；请确认文件确实下载完成，并定期移到不同磁盘。

恢复时先停止正在使用旧项目的服务，保留原文件，再直接以恢复副本的新路径启动：

```bash
# 将下载文件另存到项目目录；不要覆盖唯一的原项目。
python -m noveltool --project ../projects/restored-book.sqlite3
```

已有项目不要加 `--create`。备份中的未完成作业仍只是检查点，打开后不会自动请求模型。升级前备份使用原 Schema，可由旧版打开；升级后的备份必须由支持对应 Schema 的程序打开。

### 只读追溯

维护页可以展开最近 30 次正文 revision 的旧块、新块及差异；完整块可能含选区旁边没变化的文字，这不是整本书的历史快照。差异最多显示 600 行，完整旧/新块文本仍在页面。历史记录只读，连续撤销在正文页操作，不提供任意版本强制回退。

最近 20 条模型调用可展开请求、响应和验证结果，包括尚未集中写盘的日志。大字段各显示前 64000 个字符，并列出截断字段；关闭内容日志的请求不会伪造“原始响应”。所有内容以纯文本显示，不能当作 HTML 执行。日志可能含小说和隐私，不要随意公开。

### 退出和崩溃的边界

正常停止先取消并等待检查、生成及分析 Task，再停止自动保存循环、保存 dirty 数据，最后关闭数据库和释放进程锁。检查在等待同步时被取消，不会提前关闭仍被同步使用的数据库。强制终止不会运行这段清理：**已提交正文保留；未写盘的内存修改、未发送的浏览器内容仍可丢失。** 程序不能凭模型任务检查点恢复没有保存的作者输入。

维护 API：`GET /api/maintenance` 返回状态；`POST /api/maintenance/check` 与 `/backup` 接收 `{expected_revision_no}`；备份接口返回独立 SQLite 附件。`GET /api/maintenance/revisions/{number}` 和 `/runs/{id}` 只读返回详情。所有写/导出操作仍受同源、令牌和版本保护，不接受客户端任意文件路径。
